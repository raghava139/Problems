Phase 1 — JS fundamentalsfoundation▶

Everything async is built on these five pieces:

  • Call stack — where sync code executes, one frame at a time
  • Web APIs — browser-provided (setTimeout, fetch, DOM events)
  • Callback queue (task queue) — holds callbacks like setTimeout, DOM events
  • Microtask queue — holds Promise callbacks, runs before the callback queue
  • Event loop — moves tasks from queues to the call stack once it's empty
2
Phase 2 — Callbacksbasics▶

A callback is a function passed into another function to be run later.

  • Synchronous callback — runs immediately, e.g. array.map(fn)
  • Asynchronous callback — runs later, after some event/timer/IO
setTimeout(() => {}, 1000);
3
Phase 3 — Callback problemsproblem▶

Callback hell — nested callbacks that pyramid rightward:

login()↓ getUser()↓ getOrders()↓ makePayment()

Symptoms: pyramid of doom, hard to read, hard to maintain.

Inversion of control — you hand your callback to someone else's function and lose control over how/when/if it runs:

  • called once (expected)
  • called multiple times (bug)
  • never called (bug)
  • trust issues with third-party APIs

→ This is exactly why Promises were introduced.

4
Phase 4 — Promisessolution▶

A Promise is an object representing the eventual result of an async operation.

Pending→ Fulfilledor Rejected
  • resolve() — fulfills the promise
  • reject() — rejects the promise
  • Promise constructor — new Promise((resolve, reject) => {...})
  • Creating vs. consuming promises
5
Phase 5 — Promise chainingpattern▶
Promise→ .then()→ .then()→ .then()→ .catch()
  • Returning plain values passes them to the next .then()
  • Returning a promise chains/waits for it before continuing
  • throw inside .then() jumps straight to the nearest .catch()
  • Error propagation — errors skip .then()s until caught
6
Phase 6 — Error handling in promisespattern▶
  • .catch() — handles rejection anywhere upstream
  • throw new Error() — inside a .then becomes a rejection
  • Rejection bubbles down the chain until a .catch() handles it
  • .finally() — always runs, success or failure, no argument passed in
7
Phase 7 — Promise APIsmust-know▶

For each, know: input, output, success behavior, failure behavior, return value, execution order.

  • Promise.all() — waits for all; rejects fast on first failure
  • Promise.race() — settles as soon as the first promise settles (win or lose)
  • Promise.allSettled() — waits for all, never rejects, gives status of each
  • Promise.any() — resolves on first success; rejects only if all fail
8
Phase 8 — Async / awaitsyntax sugar▶
  • An async function always returns a Promise
  • await only works inside async functions
  • await pauses only the current async function, not all of JS
  • await does not block the JS thread

Behind the scenes: async/await is syntactic sugar over Promises — await works via promise continuations under the hood.

9
Phase 9 — Sequential vs parallel executionpractice▶

Sequential (each waits for the previous):

await fetch(...)
await fetch(...)
await fetch(...)

Parallel (fire all, then wait):

const p1 = fetch(...)
const p2 = fetch(...)
const p3 = fetch(...)

await p1
await p2
await p3

Or use Promise.all([p1, p2, p3]). Use sequential when calls depend on each other; parallel when they're independent.

10
Phase 10 — Error handling with async/awaitpattern▶ 
try {
  ...
} catch (err) {
  ...
} finally {
  ...
}
  • try — code that might throw
  • catch — handles the error
  • finally — always runs
  • throw / rethrowing — propagate an error further up

Phase 11 — Real-world API callsapplied▶

Dependent APIs — each needs the previous result → sequential:

Login↓ Profile↓ Orders↓ Payment

Independent APIs — no relation to each other → parallel with Promise.all():
